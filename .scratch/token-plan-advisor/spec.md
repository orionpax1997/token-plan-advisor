# Token Plan Advisor Agent Skill

Status: ready-for-agent

## Problem Statement

个人开发者需要在全球及中国市场众多 Coding Plan、通用订阅和 API Token Plan 之间做选择，但套餐价格、额度、模型能力、地区注册、支付方式、网络访问和服务政策持续变化，且不同 Vendor 使用不同的计费单位和限制描述。现有信息通常分散在官方套餐页、帮助中心、API 文档和公告中，用户很难在同一时间点完成可验证、可比较的决策。

静态榜单和单一价格排序不能处理以下现实问题：Coding Subscription 与 API Usage 不能直接按同一单位比较；中国用户的注册、支付、网络和政策可用性并不等价；Benchmark 数据需要转换为统一指标；官方资料可能缺失、过期或互相冲突；推荐还必须适配用户本次的预算、地区、用量和工具偏好，同时不能建立长期用户画像或代替用户执行购买和配置。

## Solution

提供一个标准 Agent Skill，作为实时的 AI Coding 套餐选择器。Skill 在每次调用时，从可插拔的官方 `Data Provider` 获取当前套餐事实，从可插拔的 `Benchmark Adapter` 获取并标准化能力指标，校验统一 Schema，按 `Plan Type` 分组，在当前会话的 `Current Decision Context` 下应用透明且可动态调整的 `Recommendation Policy`，再由 LLM 将确定性分析结果组织成 TOP 推荐和决策树。

Skill 面向个人开发者，覆盖全球及中国市场。它应明确区分 `Vendor`、`Plan`、`Plan Type`、可用性维度、数据新鲜度和 `Unresolved Fact`。无法从可信官方来源获取或验证的字段不能由 LLM 猜测；结果必须指出缺口并要求用户补充相关信息。输出只提供分析结果、证据和官方链接，不保存用户画像，不自动购买，不自动登录或配置用户账户、API Key、IDE 或 Agent。

## User Stories

1. 作为个人开发者，我想用自然语言描述自己的 Coding 需求，以便获得适合我的套餐建议。
2. 作为个人开发者，我想指定所在国家或地区，以便排除无法在我所在地区正常注册或使用的方案。
3. 作为个人开发者，我想指定预算，以便优先看到不超过预算或明确超预算的方案。
4. 作为个人开发者，我想描述每日或每月的代码任务量，以便比较套餐额度与我的实际使用强度。
5. 作为个人开发者，我想指定正在使用的 Coding Agent、IDE 或工作流，以便推荐与我的工具兼容的 Plan。
6. 作为个人开发者，我想表达对模型能力、速度、上下文长度、并发、隐私和价格的偏好，以便推荐结果反映我的真实取舍。
7. 作为个人开发者，我想在不填写结构化表单时直接用自然语言提问，以便快速开始比较。
8. 作为个人开发者，我想让 Skill 将自然语言中的需求提取为本次 `Current Decision Context`，以便后续评分具有明确依据。
9. 作为个人开发者，我想查看 Skill 实际使用了哪些本次决策条件，以便发现误解并修正输入。
10. 作为个人开发者，我想让本次输入只用于当前推荐，以便不会形成长期用户画像。
11. 作为个人开发者，我想比较 `coding-subscription`、`general-subscription` 和 `api-usage` 三类 `Plan Type`，以便理解不同购买形态的选择范围。
12. 作为个人开发者，我不希望不同计费形态被强行放进一个无意义的总榜，以便避免订阅额度和 API 单价被错误直接比较。
13. 作为个人开发者，我想看到每个候选 Plan 所属的 `Vendor`、`Plan Type`、地区范围和官方购买页面，以便确认推荐对象。
14. 作为个人开发者，我想让 Skill 每次查询主动获取最新官方数据，以便结果反映套餐页面或政策的近期变化。
15. 作为个人开发者，我想知道每条事实的采集时间，以便判断数据是否足够新。
16. 作为个人开发者，我想查看价格、额度、模型、速率、并发、上下文和限制的官方来源，以便独立核验推荐依据。
17. 作为个人开发者，我想让 Skill 同时覆盖全球和中国市场的候选 Plan，以便不局限于单一地区或 Vendor。
18. 作为个人开发者，我想区分中国大陆注册支持、支付支持、网络可访问性、服务条款和功能限制，以便避免把“技术上能访问”误认为“官方支持”。
19. 作为个人开发者，我想知道是否需要海外手机号、地址或支付方式，以便提前识别注册和付款障碍。
20. 作为个人开发者，我想知道某项中国地区限制是官方政策还是未经证实的社区观察，以便正确评估风险。
21. 作为个人开发者，我想看到来自不同 Vendor 的 Plan 被统一到相同 Schema 后的比较结果，以便跨产品阅读。
22. 作为个人开发者，我想让新的官方数据源通过 `Data Provider` 插件接入，而不改动推荐流程，以便持续扩展全球和中国市场覆盖。
23. 作为维护者，我想让每个 `Data Provider` 声明它能提供的字段、官方来源、地区范围和新鲜度，以便对数据覆盖做出可审计判断。
24. 作为维护者，我想让 Data Provider 处理官方网页、官方 API、帮助中心、状态页和公告等来源，以便适应不同 Vendor 的公开信息形态。
25. 作为维护者，我想让 Data Provider 报告抓取失败、解析失败、认证要求、来源变更和超时，以便结果不会静默使用错误数据。
26. 作为维护者，我想让 Benchmark Adapter 将不同 benchmark 的结果映射到标准化能力指标，以便不把原始 benchmark 名称直接当成可比结论。
27. 作为维护者，我想让 Benchmark Adapter 保留 benchmark 名称、版本、测试条件、采集时间、来源和适用范围，以便识别不可比的测评数据。
28. 作为维护者，我想让 Benchmark Adapter 可插拔，以便新增测评来源时不改变 Plan 的基础事实 Schema。
29. 作为个人开发者，我想看到每个 Recommendation 使用了哪些标准化事实和 benchmark 指标，以便理解它为何排名靠前。
30. 作为个人开发者，我想按“价格优先”“能力优先”“中国可用性优先”等偏好改变权重，以便获得符合当前目标的结果。
31. 作为个人开发者，我想让权重根据我的 Current Decision Context 动态调整，以便预算、任务量和地区约束能影响排序。
32. 作为个人开发者，我想看到总分、分项分、权重和主要加减分原因，以便推荐不是无法解释的黑盒。
33. 作为个人开发者，我想让硬性约束先于软性评分生效，以便不把无法注册、无法支付或明显超出硬预算的 Plan 排在可行方案之前。
34. 作为个人开发者，我想看到被排除候选的原因，以便知道它是因为地区、预算、数据缺失还是功能不匹配而落选。
35. 作为个人开发者，我想看到 TOP 推荐而不是只有原始数据，以便快速形成决策。
36. 作为个人开发者，我想看到多个具有不同取舍的推荐角色，例如低成本、综合平衡和能力优先，以便比较 Pareto 风格的选择。
37. 作为个人开发者，我想看到每个 TOP 推荐的适用人群、优势、缺点和关键限制，以便判断它是否适合我的工作方式。
38. 作为个人开发者，我想看到一个从关键问题开始的决策树，以便在不同答案下快速缩小候选范围。
39. 作为个人开发者，我想让决策树使用已验证的事实和策略条件，而不是由 LLM 临时编造规则，以便其结论可复核。
40. 作为个人开发者，我想在结果中看到数据截止时间、来源清单和官方链接，以便在购买前进行最终核验。
41. 作为个人开发者，我想让价格换算和单位换算可展开查看，以便理解月费、年费、额度和 API 单价如何参与比较。
42. 作为个人开发者，我想同时获得人类可读摘要和稳定的机器可读结果，以便阅读、复制或交给其他 Agent 继续处理。
43. 作为个人开发者，我想知道某项关键数据无法获取，以便决定是否补充信息或暂缓选择。
44. 作为个人开发者，我想针对 `Unresolved Fact` 提供补充信息，以便 Skill 在当前推荐中重新计算，而不必重新描述全部需求。
45. 作为个人开发者，我不希望 LLM 猜测价格、额度、地区政策或功能限制，以便避免被貌似确定的错误事实误导。
46. 作为个人开发者，我想让来源冲突被明确展示，而不是被静默合并，以便知道哪些结论仍然需要人工核验。
47. 作为个人开发者，我想让缺少核心字段的 Plan 不进入强排名，以便 TOP 推荐只基于足够可信的候选。
48. 作为个人开发者，我想让缺少非核心字段的 Plan 仍可作为待核实候选展示，以便不因局部缺失而完全丢失潜在选项。
49. 作为个人开发者，我想让官方数据获取失败时看到失败原因和影响范围，以便理解当前结果的局限性。
50. 作为个人开发者，我想让 Skill 在数据不完整时优先请求我补充地区、预算、工具或限制，而不是给出伪精确排名。
51. 作为个人开发者，我想确认 Skill 不会自动登录我的 Vendor 账户，以便避免暴露账号和授权信息。
52. 作为个人开发者，我想确认 Skill 不会自动购买或变更订阅，以便最终决策和付款仍由我控制。
53. 作为个人开发者，我想确认 Skill 不会自动配置 API Key、IDE、Coding Agent 或网络设置，以便避免对本地环境产生未授权副作用。
54. 作为个人开发者，我想确认 Skill 不会绕过地区限制、支付限制、访问控制或服务条款，以便使用过程符合官方规则。
55. 作为个人开发者，我想看到结果不构成财务、法律、合规或持续可用性承诺，以便正确理解推荐的责任边界。
56. 作为 Skill 宿主维护者，我想让宿主能够调用一个标准化 Skill，而不把核心分析绑定到特定 Vendor 或 Agent 平台，以便在不同 Agent 环境中复用。
57. 作为 Skill 宿主维护者，我想让用户补充的信息只保留在当前会话上下文，以便宿主可以控制长期记忆和日志策略。
58. 作为维护者，我想让 Recommendation 带有策略版本、数据时间点和来源标识，以便复现一次历史分析。
59. 作为维护者，我想让每个标准化字段保留原始值、归一化值、单位、证据和置信状态，以便排查转换和评分错误。
60. 作为维护者，我想让评分规则、淘汰规则和输出要求具有版本化定义，以便策略变化不会破坏历史结果的解释。

## Implementation Decisions

- 交付物是宿主无关的标准 Agent Skill。Skill 的说明、输入输出契约、领域 Schema、Adapter 约定和决策流程应保持可移植；宿主只负责提供调用上下文、网络访问能力和 LLM 能力。
- 核心分析流程由确定性逻辑控制，顺序为：解析 `Current Decision Context`、调用 Data Provider、校验和归一化事实、调用 Benchmark Adapter、应用硬性约束、计算动态权重和分项分、排序与生成候选解释、再交给 LLM 组织自然语言输出。
- LLM 不负责事实采集的最终裁定、单位换算、硬性淘汰、总分计算、排序或补全未知事实。LLM 只负责从已验证分析结果生成摘要、推荐理由、决策树和面向用户的补充问题。
- 每次用户查询都主动获取最新可用的官方数据。每条数据记录必须带采集时间或更新时间；结果必须展示数据截止时间。实现可以利用宿主提供的网络能力，但不能把静态缓存冒充为当前实时事实。
- 核心事实优先且原则上只接受 `Official Source`：官方套餐页、价格页、帮助中心、API 文档、状态页、公告或同等官方维护页面。第三方 benchmark 或社区观察不得伪装成官方事实；若被接入，必须单独标记来源、条件和置信状态，且不能无标记地进入核心价格、额度或地区政策结论。
- `Vendor`、`Plan`、`Plan Type`、`Data Provider`、`Benchmark Adapter`、`Recommendation Policy` 和 `Recommendation` 使用领域词汇中的定义，不使用同一个 `Provider` 名称同时表示商业 Vendor 与数据采集连接器。
- 标准 Plan Schema 至少覆盖：稳定标识、Vendor、Plan 名称、Plan Type、可购买地区、计费周期、价格与币种、额度或使用限制、模型与功能能力、上下文长度、速率和并发、隐私或数据处理说明、注册要求、支付方式、官方服务政策、官方链接、来源证据、采集时间和字段级数据质量状态。
- Schema 支持字段级状态：已验证、部分获取、过期、来源冲突、不可获取和不适用。原始值、规范化值、单位、转换说明和证据引用必须能够追溯；不得把未知、零值和不适用混为一谈。
- `Availability` 必须拆分为注册、支付、网络访问、服务政策和功能限制等维度，并允许每个维度分别表示官方支持、未确认、受限、不可用或仅有非官方观察。不存在单一的“支持中国”布尔字段作为全部判断依据。
- 三类 `Plan Type` 可由同一 Skill 处理，但默认分别比较和分别排名：`coding-subscription`、`general-subscription`、`api-usage`。只有当用户明确要求跨类型比较且存在可解释的统一使用场景时，才提供并列分析；不得把不同计费单位直接合并为一个无语义总分。
- 第一优先级场景是个人开发者选择 Coding Plan；全球及中国市场的 Vendor 和 Plan 通过可插拔 Data Provider 注册。覆盖范围不足时，结果必须说明当前已查询的来源和未覆盖的候选，不得宣称市场完整。
- Data Provider 必须声明支持的 Vendor、来源 URL 或官方 API、可提供的字段、地区范围、失败类型和数据新鲜度。Provider 的失败、超时、页面变化和来源不可访问都应形成可展示的数据质量信息。
- Benchmark Adapter 必须声明 benchmark 名称、版本、测试条件、原始指标、标准化指标、适用模型或 Plan、来源和可比性限制。没有足够上下文的 benchmark 不得转化为看似精确的综合能力分。
- `Recommendation Policy` 采用动态权重。权重由当前预算、用量、地区、工具、能力偏好、速度、隐私和其他约束影响；默认策略提供价格优先、综合平衡、能力优先和中国可用性优先等可解释偏好模式。具体数值应集中、版本化并能在结果中回显，不能由 LLM 临时决定。
- 评分前先执行硬性约束，例如明确不可注册、不可支付、违反用户硬预算或缺少必要兼容条件的 Plan。软性条件再进入分项评分。硬性约束与软性评分的结果都必须能解释。
- Recommendation 至少包含：本次 Current Decision Context 摘要、数据截止时间、TOP 推荐、每项的总分与分项分、使用的权重、优点、缺点、适用条件、关键限制、官方来源、官方链接、候选淘汰原因、Unresolved Fact、需要用户补充的信息、决策树和不自动购买/配置的责任边界声明。
- 输出同时提供人类可读摘要和机器可读结构化结果。机器可读结果至少包含策略版本、数据时间点、候选 Plan、标准化字段状态、评分明细、来源、推荐结果和未解决事实；展示层可折叠价格换算、候选淘汰和原始证据细节。
- 当关键字段缺失、来源冲突或获取失败时，Plan 不进入强排名，或降级为明确标记的待核实候选。结果必须列出无法获取的字段、对推荐的影响以及用户可补充的具体信息；LLM 不得猜测或静默补全。
- 用户补充信息后，Skill 应在当前会话中重新应用同一套确定性 Schema、约束和 Recommendation Policy，并展示哪些结果因补充信息而变化。用户输入只属于 Current Decision Context，不写入长期用户画像；Skill 不要求也不保存账号、支付凭证或 API Key。
- Skill 只提供分析和官方链接，不自动购买、登录、订阅变更、配置 API Key、配置 IDE 或 Agent，不绕过地区/支付/访问控制，不对未来价格、额度或可用性作承诺，也不提供投资、财务、法律或合规结论。
- 当前仓库没有既有业务模块或 ADR；本规格定义首个领域切入点。核心数据 Schema、评分策略和宿主接口属于可逆实现约束，暂不单独创建 ADR；若后续选择持久化缓存、特定抓取基础设施或特定宿主协议，再单独记录架构决策。

## Testing Decisions

- 最高测试 seam 是一次完整 Skill 调用：输入一个 `Current Decision Context`，注入 fixture-backed 的 Data Provider 和 Benchmark Adapter，使用受控的 LLM 生成器，验证最终人类可读结果与机器可读结果的外部行为。内部函数可以重构，只要该 seam 的行为契约保持不变。
- Fixture 必须包含全球与中国市场的代表性 Vendor、不同 `Plan Type`、不同币种和计费周期、可用性维度差异、benchmark 差异、缺失字段、来源冲突、过期数据、抓取失败和用户补充信息场景。
- 端到端测试应验证：每次查询使用当前注入的数据；结果包含数据时间点和官方来源；三类 Plan Type 默认分组；TOP 推荐符合硬性约束；动态偏好改变排序；总分、分项分和权重可解释；决策树只使用已验证条件；机器可读结果与人类摘要表达同一分析结论。
- 端到端测试应验证：官方数据不完整时显示 `Unresolved Fact`、说明影响、请求用户补充，不让 LLM 生成价格或地区政策猜测；来源冲突和 Provider 失败不会静默转成确定性推荐；缺少核心字段的 Plan 不进入强排名。
- 端到端测试应验证中国 Availability 的注册、支付、网络、政策和功能维度分别呈现，并区分“官方支持”“未确认”“受限”“不可用”和非官方观察。
- 端到端测试应验证不同 Plan Type 不被错误合并；在用户明确要求跨类型分析时，结果展示比较前提、换算假设和不可比项，而不是制造一个无依据的总分。
- 端到端测试应验证用户补充信息只影响当前调用链和后续当前会话结果，不触发购买、登录、配置或外部写操作，不要求或记录账号、支付信息和 API Key。
- Schema 和 Adapter 的契约测试应通过完整 Skill seam 间接覆盖：非法单位、未知字段状态、重复 Plan 标识、缺失来源、无效 benchmark 条件和不可比较的指标必须导致可解释的校验结果，而不是错误排名。
- LLM 测试使用受控响应和不可信响应两组 fixture，验证 Skill 能将 LLM 输出限制在已验证事实和确定性分析结果内；测试不锁定具体措辞，只锁定来源、数值、限制、结论和警告的一致性。
- 在当前代码库中不存在相关测试先例；因此采用黑盒行为测试和 fixture-backed 外部依赖替身作为首个测试模式，不以内部模块调用次数或私有实现结构作为断言。

## Out of Scope

- 自动购买、续费、取消、升级、降级或变更任何订阅。
- 自动登录 Vendor 账户，读取账户余额、个人用量或私有套餐资格。
- 自动创建、存储、轮换、注入或配置 API Key、访问令牌、IDE、Coding Agent、代理或网络设置。
- 绕过地区限制、支付限制、访问控制、验证码、登录墙或 Vendor 服务条款。
- 保存长期用户画像、跨会话偏好、身份信息、支付信息、API Key 或与推荐无关的遥测数据。
- 把全球及中国市场宣称为完整覆盖；未接入的 Vendor 或来源必须保持未覆盖状态。
- 把非官方文章、搜索摘要、社区传闻或未经条件说明的 benchmark 当作官方事实。
- 让 LLM 猜测缺失的价格、额度、限制、地区政策、能力或可用性。
- 将所有 Plan Type 强制合并为一个总榜，或把订阅额度与 API token 单价在没有明确使用模型时直接比较。
- 对未来价格、未来额度、持续可用性、服务稳定性、法律、合规、财务收益或投资价值作承诺。
- 建立持续后台监控、主动告警、价格变化通知或自动刷新任务；本规格只要求在用户查询时主动获取数据。
- 实现完整的 Vendor 数据覆盖清单、商业合作、付款集成或采购代理能力；这些属于后续 Adapter 和产品运营范围。

## Further Notes

- “实时”在本规格中定义为每次用户查询主动获取当前可用的官方数据，并披露数据时间点；不是后台持续监控或主动通知。
- “中国可用”不是单一结论，必须由注册、支付、网络、政策和功能限制等 Availability 维度共同表达。
- Recommendation 是特定时间点、特定 Current Decision Context 和特定策略版本下的分析结果，不是事实数据库，也不是对未来的保证。
- 首个实现应优先建立标准 Schema、Adapter 契约、确定性评分边界和完整 Skill 输出契约，再逐步增加 Vendor 覆盖；新增 Vendor 不应要求改写核心推荐逻辑。
- 机器可读结果应保留官方链接和字段级证据，便于宿主 Agent 后续展示、复核或请求用户补充，但不应因此改变“不保存用户画像”的边界。
